# SDD 4단계: 리뷰

산출물은 정리된 diff다. 리뷰를 QA보다 먼저 한다.

리뷰어를 모델과 에이전트로 나누는 이유: 구현한 세션은 자기 코드의 의도를 알고 있어서 결함을 놓친다. 맥락을 물려받지 않은 리뷰어가, 서로 다른 모델로, 서로 다른 관점을 보게 한다.

| 리뷰어 | 모델 | 실행 방식 | 보는 것 | 코드 수정 |
|---|---|---|---|---|
| `sdd-code-reviewer` | Opus | 서브에이전트 | 버그, 동시성, 트랜잭션, 규칙 위반 | 안 함 |
| `sdd-spec-reviewer` | Sonnet | 서브에이전트 | spec.md, plan.md, tasks.md와의 일치 | 안 함 |
| `/codex` | GPT (Codex CLI) | 외부 프로세스 | 2차 의견 | 안 함 |
| `/review` | 현재 세션 모델 | 메인 세션 | gstack 체크리스트 | 기계적인 것만 |

## 탐색

1. `~/.claude/skills/sdd-flow/scripts/status.sh`를 실행하고 "기능 폴더"를 확인한다. `tasks.md`에 남은 작업이 있으면 `/sdd-build`로 돌아간다.
2. 테스트를 실행해 통과하는 상태에서 시작하는지 확인한다. 실패하면 리뷰 전에 고친다.
3. 기준 브랜치를 정한다. 인자로 받았으면 그것, 아니면 `origin`의 기본 브랜치다. 원격이 없는 새 프로젝트면 로컬 `main`을 쓴다.
4. 리뷰 대상 diff를 파일로 저장한다. 커밋되지 않은 변경도 포함한다.
   ```bash
   git diff "$(git merge-base HEAD <기준 브랜치>)" > "${TMPDIR:-/tmp}/sdd-review.diff"
   ```
   `<기준 브랜치>`는 원격이 있으면 `origin/main` 형태, 없으면 `main` 형태다.
   파일이 비어 있으면 리뷰할 것이 없다. 사용자에게 알리고 멈춘다.

## 실행

### 1. 독립 리뷰어를 병렬로 실행한다

한 번의 응답에서 Agent 도구를 두 번 호출해 동시에 돌린다.

- **`sdd-code-reviewer`** 에게: diff 파일 경로, 프로젝트 루트, CLAUDE.md와 `.specify/memory/constitution.md` 경로.
- **`sdd-spec-reviewer`** 에게: 기능 폴더 경로, diff 파일 경로, 프로젝트 루트.

프롬프트에는 경로만 넣는다. 구현 의도, 걱정되는 부분, 예상 결론을 적지 않는다. 가설을 넘기면 리뷰어가 그것을 확인해 주는 쪽으로 기운다.

### 2. 외부 모델 리뷰 (큰 기능이거나 사용자가 요청했을 때)

`/codex`를 리뷰 모드로 실행한다. Codex CLI가 실행되지 않으면 건너뛰고, 건너뛴 사실을 최종 보고에 적는다.

### 3. 보안 감사 (인증, 결제, 개인정보, 외부 입력 처리를 건드렸을 때)

`/cso`를 실행한다.

### 4. 지적을 종합하고 검증한다

리뷰어의 보고는 주장이지 사실이 아니다. 메인 세션이 직접 확인한다.

1. 모든 지적을 한 목록으로 모으고 같은 것끼리 합친다.
2. 지적마다 해당 코드를 열어 재현 가능한지 확인한다. 리뷰어 둘 이상이 독립적으로 짚은 지적도 확인한다. 확인되지 않으면 버리고, 버린 이유를 적어 둔다.
3. 확인된 지적을 나눈다.
   - **동작이 그대로인 수정:** 바로 고친다.
   - **동작이 바뀌는 수정** (검증 규칙, 응답 형식, 상태 전이, 에러 처리 방식): 고치지 않고 사용자에게 보여 준다. `spec.md`를 고칠지 결정받은 뒤 진행한다.
   - **스펙 불일치** (`sdd-spec-reviewer`의 빠짐, 다름, 설계 이탈, 미검증, 거짓 완료): 코드를 스펙에 맞추는 것이 기본이다. 스펙이 틀렸다고 판단되면 사용자에게 묻는다. "초과"는 지울지 스펙에 넣을지 사용자가 정한다.

### 5. 수정하고 `/review`로 마무리한다

1. 확인된 지적을 고친다. 빠진 구현이 크면 `/sdd-build`로 돌아간다.
2. 테스트를 실행한다.
3. `/review`를 실행한다. 지금까지의 수정을 포함한 최종 diff를 gstack 체크리스트로 본다. 승인 요청에는 사용자가 답한다.

## 스펙 드리프트 확인 (반드시)

1. 테스트를 다시 실행한다.
2. `/review`가 자동으로 고친 부분을 `git diff`로 읽는다. 동작이 바뀐 수정이 있으면 사용자에게 보여 주고, 스펙을 고칠지 되돌릴지 결정받는다.
3. `/speckit-converge`를 실행한다. "Converged"가 아니면 추가된 작업을 `/sdd-build`로 처리한 뒤 이 단계를 다시 한다.

## 검증

1. 테스트가 통과한다.
2. `/speckit-converge`가 "Converged"를 보고했다.
3. 사용자에게 보고한다.
   - 리뷰어별 지적 수: 확인되어 고친 것, 확인되지 않아 버린 것, 사용자 결정으로 남긴 것.
   - 실행하지 못한 리뷰어와 그 이유.

## 하지 말 것

- 리뷰어 에이전트에게 수정을 시키지 않는다. 여러 에이전트가 같은 파일을 고치면 충돌하고, 스펙과 어긋난 수정을 추적할 수 없다.
- 리뷰어의 지적을 확인 없이 적용하지 않는다.
- 리뷰어 보고서를 통째로 사용자에게 붙여 넣지 않는다. 종합한 결과만 보여 준다.
