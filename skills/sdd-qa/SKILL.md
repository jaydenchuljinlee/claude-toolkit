# SDD 5단계: 테스팅

산출물은 QA 리포트다. 단위 테스트는 개발 단계에서 끝났다. 여기서는 실행 중인 앱이 `spec.md`의 인수 기준대로 동작하는지 본다.

## 탐색

1. `~/.claude/skills/sdd-flow/scripts/status.sh`를 실행하고 "기능 폴더"를 확인한다.
2. `spec.md`에서 모든 유저 스토리의 "Acceptance Scenarios"(Given / When / Then)를 뽑아 번호를 붙인다. 이것이 검증 목록이다.
3. 검증할 대상을 정한다.
   - **화면이 있는 앱:** 접근 가능한 URL(스테이징 또는 로컬 서버).
   - **백엔드, API, CLI, 배치:** 브라우저 없이 검증한다. 방법은 `~/.claude/skills/gstack/docs/qa-without-a-webpage.md`를 읽는다. 로컬 서버를 띄우는 명령과 필요한 인프라(DB, Redis, Kafka)를 프로젝트 문서에서 확인한다.
4. 앱이 실제로 떠 있는지 확인한다. 떠 있지 않으면 사용자에게 띄우는 방법을 확인하고 진행한다.

## 실행

1. **기본은 `/qa-only`.** 리포트만 내고 코드를 고치지 않으므로 스펙과 어긋날 일이 없다. 입력으로 대상 주소와 검증 목록을 명시한다: "`<주소>`에서 아래 인수 시나리오를 검증해줘. 시나리오별로 통과/실패와 근거를 보고해줘." 그리고 2번에서 뽑은 목록을 붙인다.
2. **`/qa`는 사용자가 "찾아서 고쳐라"라고 했을 때만 쓴다.** 코드를 고치므로 끝난 뒤 아래 드리프트 확인이 필요하다.
3. 브라우저가 필요한 검증인데 gstack 브라우저가 없다고 나오면, `~/.claude/skills/gstack/bin/gstack-browser-ensure` 실행이 필요하다고 사용자에게 알리고 확인받는다 (Chromium을 내려받는다).

## 실패한 시나리오 처리

- **코드가 틀렸다:** `/sdd-build`로 돌아간다. `/speckit-converge`가 빠진 작업을 `tasks.md`에 추가한다. 고친 뒤 `/sdd-review`를 거쳐 다시 QA한다.
- **스펙이 틀렸다(시나리오 자체가 잘못됐다):** `spec.md`를 먼저 고치고 사용자 승인을 받는다.
- **`/qa`가 이미 코드를 고쳤다:** 테스트를 다시 실행하고, `/sdd-review`의 "스펙 드리프트 확인"을 그대로 수행한다.

## 검증

1. 검증 목록의 모든 시나리오에 통과 또는 실패 판정이 있다. 실행하지 못한 시나리오는 이유와 함께 "미검증"으로 보고한다. 통과로 치지 않는다.
2. 실패가 0건이거나, 남은 실패마다 처리 방침이 정해졌다.
3. 사용자에게 시나리오별 결과표를 보여 준다.
